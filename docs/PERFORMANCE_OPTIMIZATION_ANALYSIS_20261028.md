# factory_demo 性能优化分析报告

> 版本说明：本报告分析的是 V1 的历史记录与代码。V1.1 已将 App.vue 职责拆到 DisplayApp.vue 与 AdminApp.vue；展示/后台及坐标功能见 [模块分离说明](MODULE_SPLIT.md)。本文的耗时仍是原50张记录，不是V1.1新性能测试。


日期：2026-10-28。分析对象：当前独立项目 `factory_demo`。本轮范围：**只分析并形成报告，不修改业务代码、配置和依赖，不新增推理、压力测试或性能实验。**

## 1. 结论与建议顺序

现有 50 张图片的历史记录表明，CPU 模型前向平均耗时 **438.01 ms/张，占已计时处理耗时的 95.22%**。读取、预处理和后处理合计约 **22.00 ms/张**。因此，如果目标是显著提高检测吞吐，应该优先评估 CPU 线程配置和 OpenVINO，而不是先重写前端或扩大数据库架构。

前端和服务层也有明确的改进机会：暂停、完成后仍以约 500 ms 间隔获取完整状态，后端重复查询最后一帧；长任务逐帧重复计算全部历史耗时的分位数。这些调整主要改善空闲资源占用、交互响应和长任务扩展性，应与模型推理加速分别验收。

| 顺序 | 建议 | 主要目标 | 当前判断 |
|---|---|---|---|
| P0 | 明确计时边界，补齐后续测量方案 | 避免把模型速度、处理速度和显示速度混为一谈 | 开始任何优化实验前先做；本轮仅设计 |
| P1 | 状态轮询按任务状态降频；减少重复完整快照查询 | 降低暂停、完成和后台页面的资源开销 | 静态代码依据充分，改动可保持较小 |
| P1 | 在本机比较 CPU 线程配置 | 寻找当前 PyTorch 路径的合适配置 | 当前固定 4 线程，尚未证明最优 |
| P1，条件项 | 目标为 Intel CPU 时，验证 OpenVINO 适配与数值一致性 | 改善占比最高的模型前向 | 方向合理，但本项目没有转换、执行或加速比证据 |
| P2 | 统计增量更新，减少长时间持有任务锁 | 避免长任务和慢数据库影响控制响应 | 当前 50 张记录不足以证明已形成瓶颈 |
| P2，条件项 | 最新完整帧显示、预览图、历史图像缓存和大结果列表优化 | 降低高帧率、大图、多浏览器的显示成本 | 应由浏览器和传输测量决定是否实施 |
| P2，条件项 | 有界流水线、读取和写入重叠 | 隐藏部分外围耗时 | 当前理论空间有限；模型加速后重新评估 |
| P3，条件项 | TensorRT、量化、更轻模型或分辨率调整 | 更大幅度的推理加速 | 分别依赖 NVIDIA 硬件、精度验证或重新训练，不属于纯前端优化 |

不建议现在直接引入 Redis、消息队列服务、多进程 API 集群，或把 SVG 全面改为 Canvas。现有证据尚未支持这些复杂度；项目的单任务、单推理实例约束也需要保持。

## 3. 已有 50 张记录的性能拆分

### 3.1 全部样本的加权均值

以下先合并 50 个逐帧样本再计算，未对 10/10/30 张的三个任务均值做等权平均。

| 阶段 | 平均耗时（ms/张） | 占已计时总量 | 当前代码口径 |
|---|---:|---:|---|
| 读取与解码 | 12.157 | 2.643% | 源文件检查、读取、图像校验和解码等读取区间 |
| 预处理 | 1.267 | 0.275% | letterbox、颜色/布局转换、张量转换及归一化 |
| 模型前向 | 438.006 | 95.217% | 当前 CPU 模型调用区间 |
| 后处理 | 8.577 | 1.865% | 有限值检查、角度解码、旋转 NMS、坐标恢复和结果组装等 |
| 合计 | **460.007** | **100%** | 上述四项之和 |

全部 50 帧合计耗时的 P50 为 **435.822 ms**，P95 为 **547.118 ms**。这不是请求响应时延或浏览器显示时延；50 张样本也不足以稳定估计复杂输入的尾部延迟。

| 子集 | 图片数 | 检测框总数 | 平均处理耗时（ms） | P50（ms） | P95（ms） | 处理 FPS：1000/均值 | 历史工作区间 FPS |
|---|---:|---:|---:|---:|---:|---:|---:|
| test | 10 | 196 | 434.772 | 427.441 | 466.434 | 2.300 | 2.258 |
| val | 10 | 209 | 528.127 | 529.543 | 561.438 | 1.893 | 1.873 |
| train | 30 | 819 | 445.712 | 432.555 | 531.407 | 2.244 | 2.208 |

对应任务 ID：

- test：`67daf076-2771-45d9-9129-e419aa4269dd`
- val：`da629d3b-e6cd-447e-9dbe-fe4a793007d2`
- train：`432ad4e5-51ef-41ee-9a26-44106c631a10`

“历史工作区间 FPS”由 `finished_at - started_at` 与帧数计算。代码在模型加载后设置 `started_at`，在最终数据库提交前设置完成时间；该值也不是完整端到端吞吐。三次任务的区间合计约 23.357 秒，区间与各帧四阶段之和的差值折合约 **7.13 ms/张**。差值可能包含快照写入、哈希、数据库、统计、调度等工作，不能把它全部归因于 PostgreSQL。历史时间戳不是专门的单调时钟性能埋点。

val 比其他子集慢这一现象，可能涉及图片实际输入形状、执行顺序、系统负载等因素；当前没有控制变量证据，不将其解释为数据类别导致的性能差异。

### 3.3 现有指标遗漏的范围

`backend/runner.py::_frame` 的 `total` 是四阶段相加，以下工作没有全部进入它：

1. 首次模型导入、加载、预热及权重哈希；适配器记录的加载预热值也不能覆盖所有首次使用准备工作。
2. 原图快照写入、源内容 SHA-256 计算。
3. 结果事务提交、汇总统计、锁等待、磁盘空间检查和部分调度。
4. 状态轮询等待、网络传输、浏览器图片解码、SVG/表格更新和实际呈现。

现有回放设置为 10 FPS，对应 100 ms 的帧间隔；当前单帧处理已经超过该间隔，所以不能把设置值当作实际吞吐。以后模型变快时，回放限速会影响任务吞吐，需要把“无限速处理能力”与“指定速度回放”分开测量。

## 4. 理论优化空间：先确定值得优化的部分

用已有平均值近似表示：

`已计时处理耗时 = 模型前向 438.006 ms + 其余 22.001 ms`

| 假设场景 | 推算已计时耗时 | 相对当前的处理加速比 | 解释 |
|---|---:|---:|---|
| 所有非前向阶段完全消失 | 438.006 ms | 1.050× | 外围阶段即便零成本，处理吞吐提升上限约 5.0% |
| 只有模型前向快 2 倍 | 241.004 ms | 1.909× | 仅用于理解主要耗时的影响 |
| 只有模型前向快 4 倍 | 131.502 ms | 3.498× | 外围成本的相对占比随之前移 |
| 模型前向耗时趋近零 | 22.001 ms | 理想极限场景 | 此时现有未计时成本和显示链路会更加重要 |

这些是数学场景，**不是 OpenVINO、TensorRT 或某种线程配置的性能承诺**。数据库、显示和其他遗漏成本加入后，完整链路的收益会不同。

读取加预处理合计约 13.42 ms，占比约 2.92%。只缓存这两项、假设命中后成本为零，已计时处理速度上限约提升 3.0%；首次遍历不同图片还会产生缓存建设成本。不能用重复读取同一批输入的缓存命中结果代表完整数据集的一次遍历性能，更不能把缓存预测结果算成新的真实推理。

## 5. 推理侧优化机会

### 5.1 CPU 线程配置：建议优先做小规模控制变量实验

**位置与现状：** `backend/inference/pytorch_obb.py::load` 设置最多 4 个 CPU 线程。当前没有比较不同线程数的记录。PyTorch 官方说明，`torch.set_num_threads` 控制 CPU 算子内部并行线程，并应在相关执行开始前设置。[PyTorch 线程设置说明](https://docs.pytorch.org/docs/2.14/generated/torch.set_num_threads.html)

**建议：** 后续在同一模型、输入顺序、batch、实际输入形状和 FP32 条件下比较 1、2、4、8 等候选值；是否继续扩大由可用硬件与前几组结果决定。记录前向、完整处理、API 控制响应及资源占用，而不是仅比较一次均值。

**预期收益：** 有机会改善占比最高的前向；当前不能给出百分比。线程更多也可能加大调度和带宽竞争，降低前端服务的响应稳定性。

**边界与约束：** 不把“全部逻辑核”自动设为最优；不通过启动多份模型竞争 CPU 来替代线程调优。不同线程条件应独立启动和预热，避免进程状态造成比较偏差。记录供电模式、后台负载和温度条件；线程调优不改变检测阈值、输入尺寸或数值精度。

**后续验收：** 在独立重复运行中观察中位数和尾部变化，并检查结果一致性、CPU 使用和控制请求时延。只有改善可重复且没有交互回退时，才建议更改默认值。

### 5.2 OpenVINO：Intel CPU 的主要适配候选

**位置与现状：** 当前只运行 PyTorch 适配器，OpenVINO 为后续接口方向，没有本项目的可运行 IR、精度对齐或性能证据。旧项目的 YOLO11 HBB 模型不是此处 YOLOv5-OBB 模型。

**建议路径：** 先导出并对齐模型原始输出，初期继续复用当前已验证的 OBB 后处理；在相同输入下验证完成后，再比较 OpenVINO 的适当性能设置。单路逐帧显示首先关注单请求延迟；离线批量处理再单独考察吞吐。官方文档明确区分延迟与吞吐目标，增加并发可能提高单请求延迟。[OpenVINO 延迟优化说明](https://docs.openvino.ai/2025/openvino-workflow/running-inference/optimize-inference/optimizing-latency.html)

**预期收益：** 直接作用于当前占比最高的阶段，是值得验证的方向；不得套用旧项目或其他处理器的加速比。

**边界与约束：**

- 此模型包含 180 个角度分类值，8 类时每个候选的输出维度涉及 `5 + 8 + 180 = 193`，不能按普通 HBB 输出格式处理。
- 当前 letterbox 使用 `auto=True`，配置的 640 不等于所有实际输入都是 640×640。固定形状导出、动态形状支持和预处理策略必须一起验证。
- 保持 BGR/RGB、归一化、候选筛选、多标签语义、角度解码、旋转 NMS 和坐标还原一致。初期把后处理留在 CPU 有利于定位差异，但需要测量转换和复制成本。
- 不默认启用低精度或宣称本机一定具备某种加速能力。FP32、可用的低精度路径分别形成结果证据；模型转换失败不能悄悄退回 PyTorch 后仍显示 OpenVINO 成绩。
- 导出与运行依赖应另列清楚，后续实施时评估与 `yolo_v5_obb` 的兼容性；本轮不安装或改包。
- 冷启动、编译与稳态推理分别统计。模型缓存只解决相应准备成本，不能把它当作每帧加速。

**后续验收：** 原始输出、最终框、类别、置信度和角度逐层对齐；设定并解释数值容差，再检查完整数据集的准确率与实际处理速度。50 张样本只用于路径打通和初步差异检查。

### 5.3 TensorRT：由部署硬件决定，当前不作为本机收益承诺

**现状与建议：** 当前执行环境是 CPU 版 PyTorch，没有 TensorRT 的实测链路。如果最终部署目标明确为 NVIDIA GPU，再为该目标制作、验证和测量 engine。

**边界与约束：** engine 的版本和硬件兼容需要明确管理；启用兼容选项也可能限制可选策略并影响性能，不能把任意机器生成的 engine 视为通用文件。[TensorRT engine 兼容说明](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/engine-compatibility.html)

还需计入主机到设备传输、设备到主机传输、同步和 OBB 后处理。GPU 异步执行条件下，普通函数返回时间不能直接视为 GPU 完成时间；应采用正确的同步或设备事件，并同时记录用户可感知的链路耗时。[TensorRT 性能测量建议](https://docs.nvidia.com/deeplearning/tensorrt/latest/performance/best-practices.html)

**后续验收：** batch=1 的实时路径先与相同语义的基线比较，再独立研究批量吞吐。FP16/INT8 分别进行准确率验证；不得将数据传输和后处理时间从产品吞吐指标中删去。

### 5.4 量化、缩小输入与更轻模型：明确属于精度—速度权衡

前向占比高意味着这些方向可能有价值，但它们可能影响小目标、长条物体、密集目标和旋转角度，不属于保持算法行为不变的简单工程优化。

**约束：** 当前权重有 8 类，而数据集有 7 类且类别编号顺序不同，例如 bottle 的编号不同，plate 没有对应 GT。先建立按名称审核过的映射和缺失类别说明，再谈 mAP、召回和量化损失。未经映射直接计算出的精度不能用于接受优化。

**后续验收：** 完整数据集的每类指标、漏检类型、角度/框偏差、处理耗时和资源占用一起报告；校准集与评估集分工清楚。不能以 50 张“看起来正确”代替完整精度验证，也不在本轮提前选定低精度默认方案。

## 6. 前端与显示链路优化机会

### 6.1 降低无变化状态的轮询频率

**位置与现状：** `frontend/src/App.vue::poll` 在一次请求完成后再等待约 500 ms；暂停、完成或查看其他页面时仍继续获取完整状态。实际频率为“请求耗时 + 500 ms”的倒数，通常低于每秒 2 次。`backend/runner.py::snapshot` 会重复查询最后一帧；重启后无内存任务对象时，还可能先查询最近任务。

**建议：** 运行时保留必要刷新频率，暂停/终态和后台页面采用更低频率；在用户控制操作和页面重新可见时立即刷新。进一步可让状态携带版本标识，只在任务版本或帧键变化时读取完整帧。数据库提交成功后缓存不可变的最新帧，可减少重复 SELECT。

**量级推算：** 忽略请求耗时，每 500 ms 一次约为单标签页每天 172,800 次请求；改为 5 秒一次时，对适用状态理论上减少约 90%。已有结果按代表性任务对象重序列化，快照 JSON 平均约 7.9 KB，持续完整轮询对应约 1.37 GB/天的模型化数据量。它不是抓包结果，不包含 HTTP 头，终态快照大小也可能不同；本机回环传输不代表公网费用。

**边界与约束：** 不能把页面不可见解释为停止后端任务；必须支持其他标签页发起任务后的状态发现。保留现有请求版本和控制操作的防竞态逻辑。新任务、重启和失败时正确刷新缓存；不得用缓存掩盖数据库不可用。5 秒仅为比较方案，不是已经确认的产品 SLA。

**后续验收：** 运行、暂停、完成、失败、切页、后台恢复和双标签页分别统计请求数、SQL 数、数据量与操作到显示的延迟。确认不会回滚到旧帧，所有控制操作仍能得到明确反馈。

### 6.2 保留上一张完整帧，原子切换图像与检测结果

**位置与现状：** `DetectionStage.vue::loadFrame` 已有取消旧请求、按帧键加载和释放 Blob URL 的逻辑；不是每次状态轮询都重新下载图片，也没有证据表明存在 Blob 泄漏。不过，新帧开始下载时会清空当前已加载状态，慢网络下可能短暂空白；如果未来新帧到达速度持续超过下载速度，反复取消可能妨碍完整帧显示。

**建议：** 保留上一张已完整加载的图像及其对应检测结果，下一张加载完成后整体切换。高吞吐情况下，显示只追赶最新完整帧，不要求每个推理结果都在屏幕停留。

**边界与约束：** 图像、框、表格、帧号必须属于同一帧；等待时明确标识当前显示帧，不能把旧图和新框叠在一起。允许跳过显示帧，不允许因此丢失需要持久化的推理结果。当前约 2 FPS 的小样本没有证明显示饥饿已经发生。

**后续验收：** 模拟高更新率和慢图像响应，观察空白时间、显示滞后与最新帧可达性，并检查取消、切任务、卸载组件后的资源释放。

### 6.3 原图与预览图分离，按真实场景决定缓存

**位置与现状：** `/api` 响应统一设置 `Cache-Control: no-store`，图像接口返回原图快照。50 张已有快照合计约 14.79 MiB，平均约 0.296 MiB/张；如果每张都以 2 FPS 显示，图像传输约为每个浏览器 0.59 MiB/s，这仍只是按文件大小推算。

**建议：** 针对远程访问或大尺寸输入，再评估服务端有限尺寸预览；历史不可变图像可采用与任务/帧/内容哈希绑定的私有缓存策略。原图继续作为追溯和下载依据。

**边界与约束：** 预览生成会新增编码成本，不能假设必然更快。坐标必须严格按原图尺寸映射；缩略图只影响显示，不得偷偷替换模型输入。缓存应有容量上限和失效规则，不包含状态接口；后续若增加认证或删除策略，必须同时审核私有图像缓存行为。

**后续验收：** 比较网络字节、首次打开时间、重复历史访问时间、编码 CPU 和缓存容量，验证图片纵横比、旋转框对齐、放大查看与原图下载。

### 6.4 密集目标时减少表格与 SVG 的无效工作

**位置与现状：** `App.vue` 接收完整快照对象，相关计算属性可能再次求值；`DetectionStage.vue` 为目标绘制 SVG 多边形和文本，结果表展示全部目标，最大检测数可达 1000。Vue 的更新机制可能避免一部分实际 DOM 操作，不能仅凭对象重新赋值就断言“每次全部重绘”。

**建议：** 先避免对同一帧重复替换数据；如果真实浏览器 profile 证明 DOM 成本明显，再考虑只显示选中目标标签、表格虚拟列表和分级显示。只有 SVG 本身确实构成瓶颈时才评估 Canvas。

**边界与约束：** 筛选数量、显示数量和总检测数需要分清；隐藏标签不能被理解成删除检测。保留缩放、选择和类别颜色语义，控制交互与渲染改造范围。

**后续验收：** 在代表性密集结果下记录长任务、更新耗时、内存和滚动响应，逐一确认框选择和表格筛选仍正确。8 个类别的简单查找目前不值得先做复杂索引优化。

## 7. 调度、统计与数据库优化机会

### 7.1 逐帧汇总改为增量均值与低频分位数

**位置与现状：** `runner.py::_work` 每处理一帧，把总耗时加入列表，再对完整列表计算均值和 P50/P95。N 帧期间重复扫描的数据规模累计随 N² 增长；10,000 帧时，单项全历史扫描的累计样本访问数量约为 50,005,000。这里没有把 NumPy 分位数实现假定为每次完整排序。

**建议：** 均值使用累计和与计数；P50/P95 每隔一个短时间窗口更新一次，并在任务终止时精确计算。10,000 帧上限下，保留耗时列表后定期计算通常足够，不必立刻引入近似分位数系统。

**边界与约束：** 明确运行中的统计可能稍有滞后，最终结果仍保持准确口径；失败帧是否计入与当前规则一致。统计不得在每个客户端请求时重新扫描整段历史。

**后续验收：** 最终均值/分位数与相同原始序列的离线结果一致，长任务统计成本不再随每帧重复增长，停止和暂停响应没有回退。

### 7.2 缩短任务锁占用，保留提交与可见性的一致性

**位置与现状：** 工作线程更新任务时，在条件锁内执行统计和 `save_frame`；开始任务的目录清单与部分数据库操作也在控制锁内。`Store` 使用一个持久连接与一个读写共用锁。数据库慢时，状态读取和控制请求可能等待；当前没有锁等待实测。

**建议：** 先测量锁等待和事务耗时，再判断是否把纯计算移出临界区、分离读取连接，或设计提交后发布的内存快照。保持一个明确的写入者。

**边界与约束：** 不能在持久化之前宣布完成或发布未提交帧；控制操作、错误状态和帧提交顺序必须可解释。若使用连接池，数据库会话级 advisory lock 需要独立管理，不能随连接归还而丢失单实例保护。当前不应直接增加 Uvicorn worker 数来绕过锁。

**后续验收：** 对慢数据库、提交失败、暂停、停止和重启分别验证状态一致性；记录控制响应与锁等待。优化不得引入重复推理、丢帧或两个进程同时占用同一任务。

### 7.3 数据库批量写入不是当前首要动作

**现状：** `Store.save_frame` 每帧一次事务，包含一条帧 INSERT 和一条任务 UPSERT；检测框已经包含在帧 JSON 中，没有逐框插入的 N+1 写入模式。两条 DML 不等于全部协议往返只有两次，但也不能按旧系统逐框 SQL 估算收益。现有帧主键和任务时间索引已经服务于主要访问路径。

**建议：** 先减少轮询导致的重复读、识别重复写入的元数据，再按实测决定是否批量提交。若使用小批次写入，必须显式接受相应的持久化延迟和异常丢失窗口。

**边界与约束：** 停止或完成前排空待写队列；进程突然退出时哪些帧可能丢失，需要在产品文档中说明。不要为了减少 SQL 把数据库提交推迟到全部任务结束。不要重复添加已有索引，或在没有 JSON 查询需求时增加通用 JSON 索引。

**后续验收：** 事务耗时、SQL 数、提交时延、失败恢复和最终帧数一起比较。当前未计时差值只有约 7.13 ms/张且包含多种工作，不支持宣称数据库优化可以使当前处理速度翻倍。

### 7.4 上传、历史导出与大结果集读取

**位置与现状：** 上传路由已经把图像解码放到线程执行，但后续写文件仍在异步路由中同步进行；较大的写入可能占用事件循环。历史导出按页读取，每页重复计数并使用 OFFSET；图像接口获取路径时也读取完整帧 JSON。前端下载使用 `response.blob()`，所以服务端逐段生成并不意味着浏览器内存零占用。

**建议：** 后续把上传的校验与落盘过程放入受控工作线程；大导出采用不重复 COUNT 的读取路径和按帧号继续分页；图像接口按需要只读取路径。浏览器导出可评估原生附件下载或兼容的文件流写入方案。

**边界与约束：** 保持当前请求体、单文件大小、像素数、格式、路径和磁盘检查；线程任务也需并发上限。导出不得改变顺序、漏帧、重复帧或隐藏失败，认证和错误反馈要保留。当前 50 帧不足以证明导出内存已经构成问题。

**后续验收：** 大任务导出期间的 API 响应、浏览器内存与内容完整性，上传失败后的临时文件清理，历史分页的前后边界。

## 8. 读取、快照与有界流水线

### 8.1 快照写入和内容哈希先单独计时

`runner.py::_frame` 保存原图快照并计算 SHA-256，这些工作在当前四阶段合计之外。它们是追溯链的一部分，不能仅为提高数字而删除。

重复运行同一数据集时，内容寻址存储可能减少重复快照；但需要保留每个任务的引用、原文件信息和哈希验证，并采用可证明安全的引用管理。对于当前约 15 MiB 的 50 张样本，直接引入完整去重存储系统收益不明确，建议先计时和观察磁盘增长。

`images.py` 使用 Pillow 做格式/像素校验，再用 OpenCV 解码。不能据此断言“执行了两遍完整 JPEG 解码”；校验成本应单独测量，也不能移除已有大图和损坏图片防护来获得表面收益。

### 8.2 流水线可重叠工作，但不能隐藏主要计算本身

**建议：** 如果后续前向已显著缩短、读取或写入占比增加，可研究读取/预处理、推理、持久化与显示之间的有界队列。保持单模型执行者，优先从少量预取开始。

**预期收益：** 在资源允许时隐藏部分阶段等待。当前模型前向占比约 95.2%，因此仅重叠其余阶段，不能据此预期数倍提升；多个 CPU 重任务同时运行还可能相互竞争。

**边界与约束：**

- 队列必须有长度上限和背压，不能无限积累大图、张量或结果。
- 显示队列可以取最新帧，持久化队列不能静默丢弃结果。
- 每个数据对象携带任务与帧标识；图像和框一起发布。
- 暂停、停止、失败和完成都需要定义队列边界；最终完成状态发布前，所需结果必须提交。
- 当前单帧推理不是随时可强制中断的操作，不能通过增加队列宣称停止立即生效。

**后续验收：** 有限队列峰值、峰值 RSS、处理吞吐、显示滞后、故障后的帧数和最终状态同时验证。先使用最小流水线，不沿用旧项目的整套服务拆分。

### 8.3 旋转 NMS 的语义与长尾限制

当前 `non_max_suppression_obb` 会先进行置信度筛选，再进行多标签展开、角度处理和旋转 NMS。`max_det` 的最终截断在旋转 NMS 之后，因此降低 `max_det` 不一定减少昂贵的 NMS 计算，更多时候减少返回结果和显示成本。后处理 8.58 ms 是复合阶段，不是纯 NMS 的独立计时。

低阈值和密集候选可能增加尾部耗时；代码的时间检查在相应 NMS 调用之后，并不是能强制打断计算的硬超时。当前未做这类压力测试。

提高置信度阈值、改成单标签或换成水平框 NMS 都会改变检测语义，必须作为算法策略变化验证，不能计入无损性能优化。后续应先记录候选数量、筛选数量和 NMS 独立耗时，再考虑等价实现或明确的候选上限策略。

## 9. 旧项目经验：哪些适用，哪些不能直接搬用

| 旧项目经验 | 当前差异 | 本项目结论 |
|---|---|---|
| OpenVINO 在旧 Intel CPU / YOLO11 HBB 上改善性能 | 当前 CPU、模型规模、OBB 输出和后处理不同 | 借鉴对齐和分阶段测量方法，不引用旧加速比作为预期 |
| 逐目标 SQL 改为批量写入，收益明显 | 当前已经按帧存储 JSON，一帧两个主要 DML | 不重复解决不存在的逐框插入问题 |
| 大图预览缓存和缩放策略优化 | 当前直接传原图，没有相同的每帧预览编码链 | 先确认网络/解码瓶颈，再权衡新增预览编码成本 |
| 固定图片重复回放时输入缓存收益大 | 当前读取+预处理仅占约 2.92%，完整遍历常为未命中 | 缓存结果必须注明冷热条件，不能代表通用推理能力 |
| 异步流水线和最新帧显示 | 当前主要计算仍在单个 CPU 前向，模型已复用 | 借鉴有界队列与图框同步原则，按需要渐进引入 |

## 10. 后续实验设计与接受条件

以下是实施下一轮优化时的计划，**本轮没有执行**。

### 10.1 固定实验条件

- 固定权重 SHA-256、代码版本、后端、设备、线程数、数值精度和 batch；记录依赖版本。
- 固定输入清单与顺序，记录原图尺寸和实际入模张量形状；配置图像大小相同不代表实际输入形状相同。
- 固定置信度、IoU、多标签行为、最大检测数和 OBB 后处理规则。
- 冷启动与预热后重复运行分开；说明文件缓存、模型缓存、预览缓存的冷热条件。
- 区分没有浏览器、单浏览器、多个浏览器及后台标签页；保持相同供电和后台负载条件。
- 50 张仅作路径和回归检查；完整数据集准确率与正式性能指标由用户后续执行，报告不提前代填。

### 10.2 建议补齐的计时与资源指标

| 层级 | 指标 | 用途 |
|---|---|---|
| 模型 | 前向、实际形状、首次与稳态 | 判断后端与线程配置收益 |
| 处理 | 读取、校验、解码、预处理、NMS/其余后处理 | 识别阶段变化和长尾 |
| 持久化 | 哈希、快照写入、事务、统计、锁等待 | 解释当前合计未覆盖的成本 |
| 任务 | 从开始请求到可用、首帧、处理完成、最终提交 | 区分启动与持续处理能力 |
| 显示 | 结果产生到状态到达、图片加载、实际显示 | 验证用户看到的延迟，而非只看推理 FPS |
| 资源 | CPU、RSS、磁盘读写、HTTP/SQL 次数、网络字节 | 判断资源占用、并发和长时间运行趋势 |

本机时延宜使用单调时钟；前后端或多机器时钟不能不经处理直接相减。GPU 路径额外区分异步提交与实际完成。日志与埋点本身也需要控制开销。

### 10.3 分三轮实施，逐轮决定是否继续

**第一轮：低复杂度、保持算法行为。** 补齐测量、轮询降频和去重、统计更新策略，再独立比较 CPU 线程配置。验证所有任务状态、暂停/停止、历史查询、重启恢复与图框一致性。

**第二轮：根据部署目标适配后端。** Intel CPU 验证 OpenVINO；只有明确 NVIDIA GPU 目标时再推进 TensorRT。每个后端单独交付模型转换、数值对齐、运行依赖和性能证据。

**第三轮：由第二轮结果决定外围优化。** 前向缩短后再检查预览、流水线、数据库和密集渲染；只有准确率边界允许，才研究低精度、尺寸或模型变化。

建议接受原则是“收益可重复、结果语义可解释、尾部和控制响应无明显回退、复杂度与收益相称”。具体 FPS、首帧时间和停止响应 SLA 尚未由用户确定，本报告不把建议值写成既定需求。
