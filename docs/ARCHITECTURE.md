# V1.3 架构与代码职责

目标是输入输出、生命周期和失败传播解耦，保持单机模块化；没有为了目录分层拆微服务。

## 1. 模块与依赖

|位置|职责|不承担的工作|
|---|---|---|
|backend/acquisition.py|持续落盘来源、完成发布与回执边界|模型加载、网页与业务归档策略|
|backend/inference|模型加载、前/后处理与引擎能力|浏览器、数据库和图片 URL|
|backend/runner.py|单任务生命周期、来源调度、保存后发布|浏览器图像解码和网络发送|
|backend/contracts.py|展示字段白名单、坐标/类别/角度投影|模型私有张量处理|
|backend/presentation.py|内存展示快照、异步预览、有界订阅|执行动作、改变推理结果|
|backend/store.py|PostgreSQL 事务和历史记录|调用模型和决定网页刷新|
|backend/app.py|组装服务、管理HTTP、展示WS/资源路由|把任意本地路径下发给展示|
|backend/display_gateway.py|AutoDL6006只读入口，仅代理展示与受控预览|管理、历史、上传、任务控制、模型与数据库|
|frontend/src/stream|连接、协议验证、配对、解码、历史适配|模型计算与数据库写入|
|DetectionStage / DisplayApp|画布与只读页面|直接发控制命令或猜引擎格式|
|AdminApp|参数、控制、历史和导出|机械动作控制|

## 2. 推理主路径与展示支路

来源交付完成的图片 → Runner 检查/解码 → 保存原始字节 → 推理适配器 → 组装帧和汇总 → Store 同事务保存 → 发布内存结果与展示请求。

展示工作线程读取已提交图片生成预览，将稳定帧身份和 URL 加入展示快照，再通知 WS 订阅者。图片缓存和订阅队列有界，旧预览允许被替代；输入检测不因预览跳过而丢帧。浏览器完成 URL 获取、解码与身份检查后才提交图与框。

## 3. 状态与数据库

最新状态和最新帧在内存维护；/api/status 不每次查最新帧数据库。服务初始化仍依赖数据库并恢复最近记录。历史路由继续查数据库。控制请求记录意图，worker 在帧边界完成状态转移；请求返回不等于当前推理已退出。

数据库提交失败不发布为成功结果，任务进入失败路径。普通快照文件与数据库事务不具备跨介质原子性。没有实现生产离线缓冲、丢弃历史后持续运行或持久化后执行策略。

## 4. 来源模式

有限模式沿用配置目录/上传和冻结清单，total 为整数。inbox 模式持续接收完成发布文件，total=null，直到后台停止；空目录等待。来源类型来自服务端配置，浏览器只传 source_id。

帧身份区分来源采集身份与运行展示会话；同一运行可消费持续来源。真实 capture_time 未提供时为空，另有发布时间，不能以文件修改时间冒充曝光时间。读取回执不等于完整生产断电事务，相关崩溃窗口与去重行为见来源说明。

## 5. 引擎替换边界

通用展示只消费 contracts 输出。PyTorch 将 BGR 原图转 RGB/CHW/FP32，经 CSL 旋转框解码与旋转 NMS 后还原原图四角点。OpenVINO/TensorRT 仍需真实导出与对应设备验证，不因存在 capability 条目而可运行。

模型类别与版本进入每个展示会话，换模型不能继续用旧类别解释新帧。当前不提供无缝热替换；原权重内容发生变化后须明确重启并核对哈希。

## 6. 历史与通用画布

管理/历史 API 保留已有 Run/Frame 结构；它们并非通用展示协议。history adapter 负责转换，纯画布接收已解码图像和原图坐标，不直接 fetch，也不理解数据库 run。下载事件仍由后台入口处理。

## 7. 实施和验收边界

本机回归使用Conda yolo_v5_obb，云端迁移使用独立factory_demo环境与显式cuda:0。适配器在所选设备预热、前向和后处理，JSON输出回到主机，CUDA计时在阶段边界同步；其他模块及展示协议不依赖设备。部署与记录见[CLOUD_DEPLOYMENT.md](CLOUD_DEPLOYMENT.md)。V1.0的50张历史约460ms不能作为云端吞吐；WS或GPU可用都不证明生产42fps。没有真实相机、编码器、标定、机械臂反馈，也没有实物去重统计。
