项目 当前信息
目标 在线输送带分拣、机械臂或剔除装置；优先降低结果到执行模块的时间

候选型号 Basler acA4096-40um / acA4096-40uc；黑白和彩色尚待选择

Basler 官方型号页显示：两种候选均为 USB 3.0、全局快门、Sony IMX255；默认分辨率 4096×2168，默认设置帧率 42.7 fps，完整传感器分辨率为 4112×2176。um 为黑白，uc 为彩色。这个默认帧率不是所有曝光、位深、传输设置下的持续实测保证。黑白型号、彩色型号、帧率限制因素。

2. 数据量与时间约束

以下按 4096×2168、42 fps 计算，采用十进制 MB/GB，不含协议、行填充及额外复制。

像素组织 单帧 每秒 有效像素载荷
Mono8 / Bayer8 8.88 MB 372.97 MB/s 2.98 Gbit/s
12 位紧凑排列 13.32 MB 559.45 MB/s 4.48 Gbit/s
以 16 位存储 17.76 MB 745.93 MB/s 5.97 Gbit/s
RGB8 / BGR8 26.64 MB 1118.90 MB/s 8.95 Gbit/s

相机的 USB3 标称 5 Gbit/s 不是应用有效带宽。RGB8 在该分辨率和 42 fps 下，仅有效像素就超过这条链路的标称速率；不能按这个组合承诺采集。彩色路线应优先验证 Bayer8 传输、主机/GPU 去马赛克；黑白路线优先验证 Mono8。两者都要以现场缺帧计数与持续采集结果确认。官方像素格式。

8 位原始图全量保存约 1.34 TB/小时；RGB8 约 4.03 TB/小时。实际压缩率由场景决定，不能套用当前小数据集 JPG 的体积。持久化策略和实时识别应分开设计。

  • 帧间隔：1000/42 ≈ 23.81 ms。
  • 每帧带面位移：0.45/42 ≈ 10.71 mm。
  • 延迟 50/100/200 ms 对应理想匀速位移 22.5/45/90 mm。
  • 42 fps 是输入吞吐要求；不自动意味着所有动作必须在 23.81 ms 内完成。流水线可以重叠，实际动作期限由几何距离、执行器准备时间和抖动余量决定。
  • 以匀速且无滑移作为初步估算：可用视觉时间 ≤ D/0.45 − 控制通信与执行器提前量 − 余量；D 必须是目标从拍摄位置到可执行位置的有效距离。
  • 视场沿带长方向的范围、目标尺寸和遮挡决定连续帧的覆盖关系。42 fps 不等于每个物体只出现一次。

3. 采集路线：先去掉必经磁盘，再评估直达显存

A. 推荐先验证：USB3 → pylon 内存缓冲 → GPU

相机 SDK 接收原始帧；采集回调只做时间戳、序号和缓冲交接，不执行模型、JPEG 编码或数据库操作。使用固定数量、可复用的缓冲；异步 GPU 拷贝完成前不能把原缓冲归还 SDK。若 SDK 支持自定义缓冲，可评估直接注册/使用 pinned memory；否则使用有界的 pinned staging pool，不能声称完全零复制。

GPU 侧按实际像素格式完成必要的去马赛克、颜色转换、缩放、letterbox、归一化和推理。缩放前去马赛克或在 Bayer 域缩放的选择会影响质量，须验证而非默认等价。异步拷贝与计算在支持的设备上可以重叠。CUDA 数据传输建议。

边界：pypylon 可用于接入验证；是否把采集、预处理等热点移至 C++/CUDA，以实测为依据。无需先把整个 Python 项目重写。

B. 条件路线：采集卡 / RDMA 设备 → GPU 显存

GPUDirect RDMA 确实允许第三方 PCIe 设备与 GPU 直接交换数据，但需 GPU、驱动、采集设备、SDK、操作系统和 PCIe 拓扑共同支持。NVIDIA 官方说明。

不能把普通 USB3 扩展卡、CoaXPress 采集卡和支持直写 GPU 的采集设备混为一谈。当前 acA4096-40um/uc 是 USB3 型号，不能直接接入 CoaXPress 采集卡。未获得厂家对这两个型号的端到端 GPU 直写支持证据前，生产基线采用路线 A。

例如 Euresys 的 NVIDIA RDMA 支持说明涉及专门的 GPU buffer API，且该方案标明 Linux 限制；这说明“支持 CUDA 显示”与“支持采集卡直接 DMA 至显存”必须分别确认。Euresys 支持说明。此例用于说明约束，不是采购推荐，也不代表所有厂商都具有同一限制。

C. 保留兼容：落盘目录 → 持续读取

用于相机软件只能落盘的部署、离线回归以及文件发布协议验证。需要临时文件/完成标记、去重、重启恢复、有限内存队列。它是支持的输入适配方式，不应成为所有生产配置的必经路径。

4. 检测结果分为三个独立消费者

执行支路：坐标、类别、角度与有效时限

检测结果产生后交给执行适配模块；不等待预览图编码、WS 发送、浏览器绘制或常规历史写入。执行模块负责坐标转换、时间补偿、目标关联/去重、命令编号、状态反馈与有效时限。浏览器不转发执行指令。

采集、检测和执行各自有计数；相机 42 fps 不意味着机械臂每秒执行 42 次。同一物体跨帧重复出现时不能重复下发抓取动作。

边界：像素 OBB 是观察结果，不是机械臂位姿。没有标定、时间基准和控制协议时，只输出观察/候选目标，不伪造世界坐标或真实控制成功。平面标定只在目标满足近似平面假设时成立；煤层厚度和物体高度变化可能要求深度信息或额外标定模型。

展示支路：数据模块生成有界预览

数据模块读取同一帧引用，异步缩放/压缩为预览图；发送结果元信息与二进制 JPEG 等预览载荷。前端按唯一 frame_key 关联，图像解码完成后一起更新图片、框、角度和统计。

预览初始可评估 5–10 fps；这是待确认的展示配置，不降低相机或检测吞吐目标。慢客户端只保留最新可显示帧，丢弃的是显示更新，不是执行目标或检测记录。避免 Base64 大图、无限缓存与每个浏览器分别重复编码。

预览宽高、缩放/裁剪变换必须随帧声明。检测坐标始终保留在原始图像坐标系，不能把缩略图坐标直接发送给执行模块。图像与结果可分消息传输，但到达顺序不作保证；必须设置未配对帧上限和超时。

审计支路：结果与选定图片异步留档

保存模型/标定版本、结果、执行反馈、必要的原图或压缩图。队列有界，记录写入失败/丢弃/重试，保留策略由业务确定。若生产要求每次动作前必须持久记录，应把本地预写日志或等效确认纳入时延预算，不能以异步化悄悄削弱一致性要求。

边界：不承诺任意存储速度下全量无损留档；不自动删除采集原始文件。是否全帧存储、事件触发存储或保留前后短时环形录像，另行确定。

5. 协议需要补充的字段

层次 建议字段与语义
帧身份 source_id、session_id、frame_id；联合唯一，重启后session变化
采集元信息 width、height、pixel_format、stride、capture_timestamp、时钟域、时间戳对应曝光起点/中心/终点的说明
检测目标 detection_id（帧内）、class_id/name、confidence、polygon_px、center_px、angle_deg、angle_convention、orientation_valid
检测版本 model_id/hash、推理参数、结果产生时间；时延测量使用可对齐时钟
执行候选 关联后的object_id、标定版本、世界/带面坐标、有效期限、编码器位置或时间补偿状态
前端预览 同一frame_key、预览尺寸、格式、原图到预览的变换

当前检测结果已有类别、置信度和原图四点框，但没有显式中心/角度字段，也没有跨帧object_id。建议图像角度约定为长边相对图像+x轴的顺时针角度，范围[0,180)，最终以适配器规范和测试确认。方形/近方形目标方向不稳定，需明确有效性；OBB的180°对称性无法提供物体头尾方向。机械臂角度应在标定后的坐标系中重新计算，不能直接复用图像angle_deg。

6. 队列不是越大越好

  • 采集缓冲只吸收抖动，不作为长期积压仓库。队列中的图像年龄比单纯队列长度更能反映是否还能用于执行。
  • 检测侧“全部处理”与“允许跳帧”不能因速度优先而静默选择；须结合视场覆盖、目标可见时长和漏检要求确认。厂商也区分LatestImageOnly与OneByOne用途。Basler采集策略。
  • 展示可默认最新帧；执行模块必须处理跨帧重复、乱序、过期及已执行目标。
  • 过载不能只在前端表现为卡顿，需报告采集遗漏、主动跳帧、超时检测、预览跳帧与审计失败等不同计数。
  • GPU stream、SDK buffer和进程间共享内存都要有明确所有权与释放时机，避免相机覆写仍在使用的图像。

7. 当前实现的具体差距

  1. 目录输入在启动时冻结文件清单，不能代表持续相机输入。
  2. _frame 在推理前写原图快照；结果保存后才供快照接口查询。现场执行关键路径要与常规留档解耦，不能只修改前端通信。
  3. 适配器固定PyTorch CPU FP32、batch 1；已有50张样本平均前向438.0 ms、处理合计460.0 ms，不能支持每帧42 fps。此基线不是4096×2168工业相机性能测试。
  4. 后处理包含CPU旋转NMS；GPU推理后若复制大量候选回CPU，后处理也可能成为新瓶颈。
  5. 原模型通常按640输入做预处理；4096宽缩小至640会减少小目标细节。输入尺寸、ROI或切片必须同时验证检出率与时间，不能只看FPS。
  6. 前端500ms轮询应改为事件推送；执行模块不经过HTTP状态轮询或浏览器。
  7. 当前服务器只允许本机访问。现场部署需明确服务边界、访问控制与部署配置；“在开发机跑通”不等于已经完成现场部署。

历史数据来源：性能记录、当前推理适配器、Runner。

8. 模拟器与迭代顺序

建立统一FrameSource输出，包含帧身份、采集时间、像素格式及受控生命周期的图像缓冲。模拟器、目录接入、pylon接入均输出该协议，推理/展示/执行不依赖具体输入方式。

步骤 工作 验证边界
1 固定帧协议、角度约定、三支路职责、时间戳定义 协议测试与图像/框匹配，不接真实执行器
2 独立相机模拟器，内存定速输出与文件落盘兼容模式 模拟42fps/突发/断流/迟到/乱序；记录实际发送速率
3 有界队列、超时统计、执行接收桩、WS预览与异步审计 压缩、慢浏览器和慢磁盘不拖住执行接收桩
4 GPU基线与TensorRT适配 真模型、真实分辨率/像素格式、OBB后处理及准确性对照
5 pylon真实相机接入 目标配置下持续采集、帧号连续性、时间戳与USB链路
6 标定、编码器/运动补偿、控制器协议 用现场几何与执行反馈验证，不以网页坐标代替

模拟器内存模式应预加载或受控预取少量源图片，避免把每次读盘解码开销误当成相机开销；可循环利用内容但帧身份与时间戳必须变化。4096×2168合成/重采样图仅用于链路负载验证，不证明真实图像的检出率。

42fps传输测试与真实模型42fps处理测试必须分开。当前CPU可用替身消费者验证队列及匹配，不得把替身吞吐写成YOLO生产性能。

9. 验收指标与待决项

主要指标：采集有效帧率、检测吞吐、采集到执行候选的P50/P95/P99及最大观察延迟、超时率、对象重复下发率、遗漏率、队列最老帧年龄、各支路丢弃计数、持续运行的显存/内存/磁盘增长。平均FPS不能代替这些指标。

GPU计时应使用正确同步或CUDA事件；跨相机、主机、控制器比较时间戳前先处理时钟对齐。不同阶段可能重叠，不能把各阶段吞吐时间简单相加当成准确端到端延迟。

尚需确定：um或uc、实际像素格式和曝光；GPU/系统；视场与最小杂物尺寸；拍摄至执行距离；是否有编码器/深度；执行器协议与提前量；是否要求逐帧检测以及允许的漏检/跳帧规则；图片保留策略。带速已确认0.45m/s，其余未知项不设虚构指标。

推荐优先验证当前USB3相机+pylon内存取帧+GPU推理路线。GPUDirect作为硬件配套明确后再评估的选项；目录读取保留为兼容源。三个输出支路使用同一身份协议，执行支路无需等待前端完成图片与结果配对。
