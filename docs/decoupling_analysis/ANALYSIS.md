# 通用展示模块与推理后端解耦分析

2026-10-28 · 对照 test_demo 当前源码 · 设计提案，尚未实施

## 1. 结论与本轮边界

沿用 test_demo 的“推理后端—数据适配层—展示前端”职责划分，并保留独立管理入口；进一步把执行结果、预览图片、历史归档拆为不同消费路径。通用展示只依赖稳定的展示协议，不直接依赖 YOLO、OpenVINO、TensorRT、相机 SDK、数据库表或本地文件路径。

解耦首先是输入输出、生命周期和失败传播的解耦，不等于每个模块都要变成独立 HTTP/WS 服务。第一阶段采用单机模块化实现即可，保持独立接口与有界队列；是否分进程应由实测瓶颈、依赖隔离和故障隔离要求决定。原始图像在本机尽量传受控引用，避免仅为了分模块重复序列化大图。

本轮只检查代码、形成报告和架构图；不改业务源码，不重启服务，不运行推理，不迁移数据库。原有手册和教程继续描述已实现版本，本提案独立存放，不能当成已完成的新功能。pylon 内存取帧作为生产主路线仍待用户确认；本次接口设计同时容纳目录读取和 SDK 两种来源，不替用户作此决定。

## 3. 不能直接照搬的耦合

### 3.1 检测结果等待图片编码

test_demo/backend/simulator.py 的 prepare_frame（164 起）先 frame_message，再经 PreviewCache 生成 JPEG（190–210），最后返回 message 与 jpeg。frame_message 内还同步执行 retention.apply（141）。ReplayStream.produce 等待完整包后才交给发送队列（约 420–447）。

约束：执行模块获取识别结果时不能默认等待 JPEG 编码、图片发送或普通历史写入。预览需要图片与检测对应，但执行只需及时、完整、可追踪的识别数据。

### 3.2 历史写入背压传到实时上游

fastapi/main.py:319 的 PlatformWriter.add 在 pending_count 达到 MAX_PENDING_EVENTS 后等待容量；pump:508 在广播前 await writer.add。因此数据库持续不可用、待写队列达到上限时，上游接收和实时转发会等待。这是原项目为保证记录完整性作出的取舍，不是“用了异步”就已隔离。

约束：新系统要明确普通归档故障与必须持久化后才允许动作的区别。采用异步归档，也必须定义容量、满队列事件、可容忍缺口与停机条件；不能同时承诺无限离线、有限内存、全量不丢和永不阻塞。最终现场策略待确认。

### 3.3 生命周期与展示订阅相连

fastapi/main.py:539 的 lifespan 只构造 StreamHub；首次 subscribe:450 调用 start，才启动上游 pump。backend/simulator.py:535 的 WS 会话启动 ReplayStream。断开某个浏览器不等于立即停推理，但服务启动后的首次采集依赖首次订阅，上游会话断开也影响生产循环。

约束：生产服务必须在无浏览器、浏览器重启或全部退出时仍按后台运行策略采集、检测和发送执行候选；展示连接只控制订阅，不启动或停止生产。

### 3.4 展示和操作权限混合

fastapi/main.py:580 允许实时展示连接转发 pause/resume/restart；frontend/src/stores/imageStream.js 也包含这些动作。

约束：factory_demo 展示模块保留筛选、缩放、坐标查看、连接重试等本地操作；模型切换、采集控制、检测启停、参数修改只放管理模块。只拆两个页面不等于权限隔离，生产部署还要在服务端区分只读和管理能力。

### 3.5 表面统一但语义仍不同

test_demo/backend/inference.py:106 将 detectionId 同时放入 trackId，实际是图像内检测标识；fastapi/DATA_INTERFACE.md 却把它写成跨帧跟踪标识。adapt_frame:71 转发 polygon 时没有保留原始 obb.angle；指标缺省为 0 也会混淆“未测量”和“测量为零”。

约束：detection_id 与 track_id 必须分开；没有跟踪时 track_id 为 null。没有可靠方向时 angle 为 null 并给出有效性，不能用 0 伪装已测量。未接入/未测量的准确率和健康指标必须为 unknown/null，不能显示模拟正常状态。只统一 JSON 字段名不能解决这些问题。

## 5. 推荐模块边界及各自约束

### A. 采集模块 acquisition

职责：目录读取、模拟拍照、未来 pylon 采集；分配 source_id/session_id/frame_id、采集时间和原始帧描述；交付 FrameRef。

约束：不加载模型、不编码展示 JPEG、不写业务结果表。文件源只接收完成发布的文件（生产者关闭后原子改名或 ready 标记）；目录事件配合补扫。SDK 缓冲不能在下游仍使用时归还相机。缓冲必须有总字节与帧数上限，记录入队时间、帧龄、采集丢帧和溢出原因。暂停检测不自动等于暂停相机。

### B. 推理模块 inference

职责：load / describe / predict / close；分别提供 PyTorchOBB、OpenVINOOBB、TensorRTOBB 适配器，输出统一 DetectionResult。引擎私有的归一化、letterbox、张量布局、NMS、坐标还原由适配器负责。

约束：不访问数据库、浏览器或机械臂；不把 torch.Tensor / OpenVINO 对象 / CUDA 指针写进通用结果。保留 frame_key，不重新分配。能力描述须说明图形类型、输入尺寸、精度、设备、模型类别和版本。未实现/硬件不支持应显式不可用，不偷偷切 CPU 或伪造结果。三种引擎名字不意味着吞吐、数值或 OBB 算子已验证等价。

### C. 运行编排 runtime

职责：启动/停止来源与推理，选择适配器、冻结配置版本、维护有界调度队列，按统一结果分发给三个消费者。

约束：不直接拼 HTML、不承担持久化细节。不得因为没有观看者而停采集。运行时更换模型应切换明确的会话/配置版本并排空或作废旧结果，不默认支持无缝热切换。容量满、结果过期和消费者不可用都有可观测计数；每个分支独立策略，不能一个慢消费者隐式拖住全部分支。

### D. 数据与预览模块 presentation

职责：结果格式校验、读取受控帧引用、异步缩放压缩、按帧身份配对、维护最新完整展示包、提供只读 WS 流与连接快照。

约束：不是所有原始图像和执行数据必须经过的中转站；不负责推理和控制决策。预览可以降采样/淘汰旧包，但不改变检测结果或待执行队列。预览尺寸、裁剪偏移和变换必须显式提供。数据失配、图片解码失败或超时不能配上最近一帧的检测框。必须释放 Blob/帧引用，慢预览不得长期占满采集缓冲。

### E. 通用展示模块 display_frontend

职责：消费 ViewFrame、状态及类别目录，显示图片、HBB/OBB 多边形、类别、置信度、中心/顶点坐标和有效角度，提供本地筛选与缩放。

约束：不导入引擎包，不读取本地目录，不推断某个模型的类别顺序，不发生产控制命令，不计算物理动作坐标。第一版通用范围是二维检测 HBB/OBB；分割、姿态、3D 点云需要后续协议及渲染扩展，不能宣称任意 AI 任务自动适配。缺少模型/引擎名称仍可显示合法结果。无检测成功帧与处理失败必须区分。

### F. 归档与管理 storage / management

职责：持久化结果与选定图片，历史查询、运行配置、引擎能力与服务管理；对接独立 admin_frontend。

约束：历史记录和实时预览可以暂时不同步，界面要给出数据时间和归档状态。数据库主键只在该模块内部使用；展示帧身份不能依赖数据库自增 ID。统计须标注是帧数、检测实例数还是去重物体数；不能对降采样后的预览求和冒充生产总量。是否强制落盘后再动作是现场策略，不能本轮默认改变。

### G. 执行对接 execution

职责：接收 DetectionResult；后续进行物体关联/去重、标定坐标转换、输送位移补偿、动作期限检查、命令 ID 和反馈处理。当前仅规划与记录型接口，未连接执行器。

约束：独立于 JPEG、WS 展示和浏览器。识别结果不是机械臂命令：图像 px 不等于现场 mm，OBB 长轴角不等于末端姿态；180° 对称框无法自动判断头尾。动作已过期或不确定是否执行时，不能盲目补发。相机断线、无目标、推理失败、过期结果是不同状态。机械/PLC 的联锁和最终动作保障需要现场方案，不能由网页连通状态代替。

## 6. 三层数据契约

### 6.1 进程内部 FrameRef

包含 frame_key、width/height、pixel_format、stride_bytes、capture_time/clock_domain、buffer_handle 和释放约定。目录路径、共享内存标识、SDK 缓冲或未来设备缓冲由来源/运行时私有管理；FrameRef 不发送给浏览器。第一版实现 CPU 缓冲即可，不提前实现所有 GPU 内存协议。

同一帧多消费者时必须约定所有权：谁 retain、谁 release、慢分支何时放弃引用；引用计数或租约可以选一种简洁方案。需要跨进程时另做句柄适配，不把 Python 对象引用直接当 IPC 协议。

### 6.2 引擎无关 DetectionResult

建议字段如下，正式 schema 版本与角度细节在实现前冻结：

|字段|语义与约束|
|---|---|
|schema_version|主版本不兼容时明确拒绝；未知可选字段可忽略|
|frame_key|source_id + session_id + frame_id；frame_id 建议序列字符串，避免 JS 大整数精度问题；重启必须新 session|
|model_id / model_version / config_version|可追溯模型、类别目录与参数；引擎是说明性元数据，不是展示分支条件|
|source_width / source_height|原始采集坐标系尺寸，绝不替换为 640×640 推理尺寸或缩略图尺寸|
|capture_time + clock_domain|时间戳要说明曝光开始/结束或回调时刻；跨主机时钟未同步不能直接相减|
|status / error|ok 且 detections=[] 表示未检出；error 不等于空检测|
|detection_id / track_id|前者帧内唯一；后者可空且只能来自实际跟踪模块|
|class_key / class_id / label|class_key 属于有版本的类别目录；不能假设两个模型 class_id=0 都是同一类|
|score|有限数值，范围 0..1；不作为识别准确率|
|geometry_type / polygon_px / center_px|HBB 与 OBB 都可提供顺序一致的四角点；原图像素坐标，左上原点，x 右 y 下；采用图像连续边界约定 [0,W]×[0,H]，像素索引另用 [0,W-1]×[0,H-1]|
|angle_deg / angle_convention / orientation_valid|候选规范：长轴相对 +x 顺时针、[0,180)；正方形或无方向证据置无效；HBB 的包围框方向不能冒充目标方向|
|timings|阶段起止、时钟域或时长；推理耗时、结果帧龄和端到端延迟分开|

适配器必须反转引擎的 resize/letterbox，再输出原图坐标。越界框的原始几何与用于绘制的裁剪策略需要分开，不能随意逐点截断四边形后继续把它称作真实 OBB。近正方形的角度无效阈值需要根据任务验证，不在分析阶段虚设。

### 6.3 浏览器 ViewFrame

由 DetectionResult 的只读投影、类别目录版本和 PreviewImage 组成。PreviewImage 包含同一 frame_key、preview_id、编码类型、实际宽高、source_to_preview 变换和图片载荷。例：完整原图 4096×2168 缩至 1024×542，sx=sy=0.25；原图点 (2048,1084) 应绘制在预览点 (512,271)，读出的原图坐标仍为 (2048,1084)。裁剪或补边时还需平移项。

推荐 WS 二进制展示包携带可解析的长度头、JSON 元数据与 JPEG，使帧身份和图片在应用层属于一个完整包。协议必须给出字节序、头长/图片长度上限、MIME、缺包/超长拒绝规则；第一版不要把大图转 Base64。也可以保留“JSON + 下一条 JPEG”的方案，但必须单发送者串行、连接代次隔离、严格配对与断线清空；不能依靠“最近一个 JSON”跨线程或跨连接猜测。WS 在单连接内的有序传输不等于业务级帧关联已解决。

浏览器配对和解码完再原子提交画面与框；连接恢复先获取会话、类别目录、最新完整帧快照。旧连接和旧会话的异步解码结果必须作废。图像没到时可以显示“结果已到、预览待到”，不能把框画到旧图上。

## 7. 通信选择：不把 WS 当成模块化本身

|路径|建议方式|原因和边界|
|---|---|---|
|同机采集→推理|函数接口 + 有界帧引用队列；必要时共享内存|原始帧不强制走 HTTP/WS，不新增不必要的大图复制|
|推理→结果消费者|类型明确的事件接口 + 分支独立队列|先分离职责和背压；第一版不必引入消息中间件|
|预览/状态→展示|WS 推送 + 初始/重连快照|事件到达即可更新；慢浏览器只影响自己的队列|
|管理页面→运行服务|HTTP 请求响应|配置版本、启停结果和错误易确认；无需把低频操作改成 WS|
|历史/导出|HTTP 分页查询与文件下载|读取归档，不占实时预览队列|
|结果→执行设备|先定义执行端口，现场协议待定|不承诺普通 WS、HTTP 或 Windows 程序提供硬实时保障；应按控制器能力与时限选择|

展示 WS 不应成为识别结果到执行器的必经路。前端只连接展示服务及必要只读快照；后台页面连接管理/历史服务。部署时可以使用同一个服务进程和端口，但路由与依赖边界要清楚。

## 8. 最小目录改造建议

以下是职责映射，不要求每项立即成为一个服务，也不要求建通用插件平台：

```text
backend/
  contracts/             # 帧、检测结果、展示包与版本校验
  acquisition/           # directory、simulator，未来 pylon
  inference/             # 公共接口 + pytorch_obb / openvino_obb / tensorrt_obb
  runtime/               # 生命周期、调度、分发、队列指标
  presentation/          # 配对、预览编码、WS 订阅与快照
  storage/               # 结果/图片归档、历史查询
  execution/             # 执行对接接口；本阶段仅记录型接收器
  app.py                 # 装配与路由，不堆业务逻辑
frontend/src/
  stream/                # 传输、配对、状态 → ViewFrame
  components/            # 纯展示画布与面板
  DisplayApp.vue         # 只读组装
  AdminApp.vue           # 管理入口，继续与展示分离
```

共用 contracts，具体模块由 app/运行时装配；推理不能反向 import presentation/storage，画布不能反向 import api/engine，历史仓储不能调用推理。暂不为了目录整齐搬动无关代码。

## 9. 迁移顺序与可验证成功标准

|阶段|工作|验收|
|---|---|---|
|1 固定协议|定义 DetectionResult/ViewFrame，保留现有结果兼容适配器|现有真实结果经转换后图片尺寸、类别和四角点一致；错误/空检测语义明确|
|2 展示解耦|把取图/轮询移到 stream，画布只收 ViewFrame|断开真实后端，用独立模拟服务即可展示；换模型类别无需修改组件|

通用性核心验收：同一份前端构建产物，接入 PyTorch 后端、独立协议模拟后端，以及将来真实 OpenVINO/TensorRT 后端，不改展示源码即可显示。每个后端都必须正确实现同一契约，不能要求未经适配的任意输出直接兼容。

失败场景：两个浏览器不同网速、数据库持续断开、图片缺失/迟到、结果乱序/重复、会话重启、模型类别变化、错误坐标/NaN、连续流无总帧数、缓冲耗尽、执行反馈超时。测试要检验串帧、资源释放和失败传播，而不只是页面能打开。

## 10. 与现场参数的关系及待定事项

用户提供：acA4096-40um / uc 候选相机、目标 4096×2168 且至少 42fps；+8.00m 平面 2206# 转载带式输送机，带长 9m、带速 0.45m/s。+8m 不按相机安装高度解释，9m 不按相机到执行器距离解释。单色/彩色、像素格式、GPU、操作系统、编码器、视场和执行位置仍未定。

按 42fps 计算帧周期约 23.81ms，带面每帧移动约 10.71mm；这些只是输入条件推算，不是系统实测性能或实时性承诺。最晚动作窗口依赖实际拍摄到执行距离、动作耗时和安全余量。解耦后不会自动达到 42fps，更不能把预览 5–10fps 当作推理满足 42fps 的证据。

不阻碍固定展示协议的待定项：GPU/操作系统、相机 Mono/Bayer 格式、执行设备协议。影响运行策略、须在实现对应路径前确定的项：生产取帧是否采用 SDK 内存主路线；过载时是减速/停机还是允许哪类帧跳过；归档失效是否禁止动作；真实物体覆盖率和去重需求。速度优先不自动授权丢弃待检测图片。
