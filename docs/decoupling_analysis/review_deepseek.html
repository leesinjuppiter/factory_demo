4. 需要修正后再采纳

4.1 不能只改 /status 就称为“断开数据库依赖”

当前 app.py:82 在服务启动时构造 Store；数据库不可用会影响整个服务启动。control 路由在 Runner.control 之前先 get_run 查库（231–233）；图片路由也先 get_frame 查库（245–246）。因此即使 /status 改为内存读取，暂停请求、首次加载图片、刷新页面和冷启动仍可能受数据库影响。

“已有网页保留 Blob”与“数据库断开后新打开网页还能取到图”是两个不同验收场景。应分开定义状态读取、最新预览、历史查询、控制与服务冷启动的可用性。预览 URL 若要摆脱数据库，就必须由展示服务的独立缓存/映射提供，不能继续指向现有查库图片端点。

4.2 “锁外写库”不是直接移动一行代码

当前 worker 复制 run、更新计数、写库，再 run.update(updated)。若释放锁期间控制端把任务改为 stopping，worker 随后写回旧的 running 副本，可能覆盖停止意图。单 writer 也需要解决帧事务、配置版本、控制命令和最终状态的顺序。

建议先写状态转换与提交规则：运行状态和最后帧在短临界区发布一致快照；异步结果按 session/run 与 revision 验证；控制意图不能被旧快照覆盖。分别标记“暂停已请求”与“已在帧边界暂停”。控制受理迅速不代表已强制中断当前模型调用。

API 请求取消只结束浏览器等待，不证明服务端 SQL 已取消；把超时从 10s 改成 2s 不是解耦本身。需要避免反复超时重试堆积服务端等待，同时通过数据年龄标识陈旧状态。

4.3 angle 的两种问题同时存在

DeepSeek 指出旧模型是 HBB、angle 硬编码 0，这一点正确，我上一轮将其简称为“后端角度未传出”容易让人以为旧模型已预测旋转角，应修正。准确说法是：旧后端的 obb.angle=0 只是兼容字段，不是有效目标方向；Adapter 同时确实未转发该字段。只补转发无法获得真实角度。

归一化 polygon 本身不是设计错误；错误在于两个坐标空间同名且未转换。新契约选原图像素有利于本项目，但不能据此否定旧归一化协议。只在确需接入旧输出时增加兼容适配器，不迁移旧平台/CVAT 数据库。

4.4 未知不能用 0，但 0 可以是有效值

“ms(0) 不再当有效值”不应采用。帧数 0、队列深度 0、零丢帧、合法水平角 0° 都可能正确。应改变未知值的生产方式，使用 null/quality；格式化器继续正确显示合法 0。

也不必把每个内部计数字段都包装成五字段对象。先给跨来源、估算或易误解的外部指标增加 source/quality/measured_at；单位可在协议中固定，基础计数仍可保持简单类型。连接成功和结果新鲜度分开，模型慢不等于 WS 断开，WS 连着也不保证有新帧。

4.5 JSON + URL 合理，但需要缓存生命周期

同一 preview_id 的 URL 内容必须不可变，不能不断覆盖 /latest.jpg；URL 要包含或绑定明确帧身份。浏览器只在图片解码成功后提交对应框；旧会话的异步结果作废。

有限缓存可能使迟到请求收到 404/410，应明确展示为预览已过期并请求新快照，而不是配旧图。缓存保留窗口、浏览器并发下载数、失败重试次数均有界。实时预览的保留与历史长期保留不是同一个承诺。WS/HTTP 混合不破坏通用性，具体传输被 stream 层隔离即可。

4.6 调整过度或过早的约束

“采集与传输不能在同一个文件”不宜成为硬规则；真正要限制的是调用依赖、资源所有权与生命周期。可以在小文件中清晰分工，不为目录整齐搬代码。

可以暂不实现共享内存/GPU 句柄，但不能推迟像素格式、CPU 缓冲所有权与连续/带行填充约定。初版若只接受连续 BGR uint8，应显式写明，并由读图适配器完成转换。

模型显示版本不必等于 hash。建议 model_id/model_version/artifact_hash 分开；导出产物还应可关联原始模型，配置指纹覆盖实际生效默认值。hash 是可追溯字段，不证明模型数值一致。

4.7 时间、角度与幂等要补限定

JSON 里的纳秒整数若用浏览器 Number 接收会超出精确整数范围；建议十进制字符串或另选明确精度的时间表示。相机没有真实采集时间时 capture_time 应为空，另记录 file_ready/ingest/replay 时间，不能伪造曝光时刻。相机时钟与主机单调时钟不能不经映射直接比较。

polygon 的起点标准化可用于固定测试，但最低 y 点随噪声会变化，不能当跨帧对应点。角度误差按 180° 周期计算；近方形方向无效判据待数据验证，不能现在虚设一个阈值。跨引擎测试应按类别与几何匹配目标，不用返回数组下标一一比较。

result_id 用于投递去重；同一帧同配置的有意重算需要明确 evaluation_id/attempt 语义，不能一律丢弃。执行命令还需独立 command_id、物体关联和反馈，重复消息被去除不等于真实设备动作保证恰好一次。

4.8 性能和故障注入表述需收紧

460.007ms 的倒数约 2.174fps；438.006ms 前向的倒数约 2.283fps，不能把两者都写为实测 2.3fps。1 GiB / 372.965MB/s 约 2.879s，不是 2.7s，而且这是字节量等价时间，不是当前实现真的能安全再运行这么久。

“retention 复制比 JPEG 编码更重”没有本轮时序测量支持。文件编码、大小、缓存命中和磁盘状态都会改变结果。解耦本身不加速模型，但并行重叠可能改善端到端吞吐，故“解耦不会提升吞吐”应改为“不保证提升，更不保证达到 42fps”。

“停 PostgreSQL / kill -9”不是只读注入，也不是本轮授权操作；重启测试应使用隔离测试进程/数据库及本机平台适配方法。优先以替身或独立测试连接模拟故障，不停止共享服务。文中的 1–2/3–5 人日只是未经拆解验证的估算，不作为交付承诺。

7. 落盘路线的容量估算与约束

按 4096×2168 计算，Mono8/Bayer8 纯像素每帧 8,880,128 字节；BGR8 解码缓冲为其 3 倍。下表均为理论量，不包括协议、文件头、行填充、数据库索引或文件系统放大。预览固定假设 200 KiB/帧，仅用于估算，不是实际压缩结果。

输入/消费频率Mono8 原始字节 MB/sBGR8 缓冲字节 MB/s200 KiB 预览 MB/s若每帧一个事务：事务/小时
2fps17.76053.2810.40967,200
5fps44.401133.2021.024018,000
10fps88.801266.4042.048036,000
42fps372.9651,118.8968.6016151,200

42fps 采集而 5fps 预览时，只降低预览栏对应的数据量，不降低采集落盘量。若实际文件压缩，磁盘写入按实测文件大小计算；按原始像素字节估算不能冒充实际 JPEG 大小。

若相机已写原图，程序每帧又完整复制一份，应用层写入量约翻倍；实际介质读写还受系统缓存影响，不能简单称为硬盘必然承受两倍物理 I/O。要避免重复快照，必须先确定相机文件不可覆盖、保留期限、读取确认与清理责任，不能只删 write_bytes。

新增需要注意的现有限制：单文件最大 20 MiB，原始 BGR8 4096×2168 约 25.41 MiB（不含文件头），无压缩彩色 BMP 会超过当前限制。Mono8/Bayer8 约 8.47 MiB，但当前解码采用 BGR 输出，内存需求会增大。目录上限 10,000 张按 42fps 约 238.1s 就达到，因此固定清单逻辑不能当持续目录队列。

文件契约优先固定：同一文件系统内临时名写入、关闭后发布最终名或明确 ready 标志；没有发布协议时“大小稳定一段时间”只是启发式；每帧唯一身份、重启会话、时间信息；消费者只读已发布文件；未处理/已处理/失败/过期的状态；首次启动和漏事件补扫；按顺序键取图而非猜文件时间；磁盘积压与内存解码队列分开。

模拟拍照脚本近期应覆盖：正常发布、写入延迟、突发、坏文件、重复通知、进程重启，以及文件保留边界。源读取可通过独立模拟接收端验证 42fps 输入发布；真实推理仍单独测吞吐，不能称全链路已达标。

队列容量按字节、帧数、最老帧龄描述，数值等动作时限和实测资源明确后再定。磁盘能存很多图片不代表图片还有执行价值；目前不具备拍摄到执行距离，不设置虚构动作截止时间，不默认丢待检帧。

8. 修订后的近期顺序

1. 冻结展示 v1 契约：身份、坐标、角度、类别版本、时间、空值、错误、连续流状态。明确同一前端构建接不同后端的范围为 HBB/OBB 二维检测。

2. 建立固定协议样例和独立模拟后端，先验证新前端不依赖真实模型/数据库；保留真实 PyTorch 兼容适配。同步验证实时页与后台历史页。

3. 抽取展示数据层，维护已配对画面；采用 WS JSON 事件 + 受控不可变预览 URL 作为候选 v1。将数据库连通与画面新鲜度拆开，不承诺新生产容错策略。

4. 在明确状态转换后缩小锁范围、提供一致的内存状态快照；保留当前已接受的写入失败语义，直到用户决定生产归档规则。不可把“状态仍可见”写成“生产继续运行”。

5. 同阶段准备文件来源契约与模拟拍照脚本，替换冻结目录清单的假设。相机 SDK 与硬件优化不是该模拟器的前置条件。

6. 后续依据实测接入真实 OpenVINO/TensorRT、确定生产归档容错和执行协议。二进制包、共享内存等以明确瓶颈为触发条件，不预先铺设复杂框架。
